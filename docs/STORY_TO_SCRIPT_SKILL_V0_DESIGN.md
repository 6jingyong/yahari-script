# 故事转剧本 Skill v0：先建立场景契约

> 2026-09-27 设计记录。事实账本、场景契约和语义警告已在网页流程实现；个人技能 `yahari-story-to-script` 已安装。下文保留部分后续扩展方向。

## 结论

目录继续保持 **作品 → 章节 → 场景**。不把人物、线索、对白或动作加成目录节点。真正需要增加的是生成过程中的一层不可见规划：**故事事实账本 + 场景契约**。它们约束模型写每场的内容，最终仍输出当前 `ScriptDocument`，由同一个 Adapter 校验和编译。

第一版 Skill 命名 `yahari-story-to-script`。当前网页在写对白前先确定每场的入口状态、必要变化与出口状态，再检查生成结果有没有越过证据边界。模型请求顺序是大纲、账本与契约、逐场台词、逐场可选审阅。

## 两个案例暴露的问题

| 案例 | 容易写错的地方 | 场景契约必须约束的边界 |
| --- | --- | --- |
| 《九点的影子》 | 把“证人看见人影”直接写成“被告从东门逃走”；停电后还肯定看清外套颜色 | 证词是人物主张；停电是记录事实；镜像方向是可论证解释。结尾只能撤回“亲眼看见东门离开”，不能顺手证明被告无罪 |
| 《消失的十三秒》 | 把“录音被剪辑”直接写成“被告原话无罪” | 剪辑与时长差异可确认；缺失部分的内容未知。结尾是暂不依赖导出文件，等待核验原件 |

当前 `StoryOutline` 的场景只有 `title / summary / background`；`scenePrompt` 依赖整个故事、大纲和上一场末尾对白。摘要既承担给读者看的功能，又被当成机器约束，无法区分**已证事实、人物说法、推断和未知**。上一场八句台词也不足以保存跨章节的人物知识和伏笔。

## Skill 的输入与产物

输入：原故事或梗概、改编模式（`忠实改编 / 允许扩写 / 原创续写`）、作者约束、目标 Adapter 与 Content Pack 的能力清单。未提供的设定保持未知；原创模式允许添加事实，但必须标记为新创作。

Skill 在导入编辑器前产生四种数据：

1. **故事账本 `StoryLedger`**：人物、时间点、地点、事件、线索、证据来源、相互冲突的说法和未解问题。每条记录带 `kind: established | claim | inference | unknown | invented`。忠实改编中，`established` 和 `claim` 附原文片段位置；模型不能凭空标记为原文事实。
2. **目录大纲 `StoryOutline`**：作品摘要、章摘要、场景标题和供读者看的短摘要。它对应现有三级目录，不承担全部生成约束。
3. **场景契约 `SceneContract[]`**：每场的参与者、地点/时间、入口知识状态、场内目标与阻力、必须发生的转折、允许揭示的事实、禁止提前揭示的事实、出口状态。契约以稳定 `sceneId` 引用账本条目。
4. **剧本文档 `ScriptDocument[]` 与 `Diagnostics[]`**：台词和动作使用目标 Adapter 的现有能力；诊断指出硬错误与需要作者判断的语义疑点。

场景契约示意（缩减版）：

```json
{
  "sceneId": "shadow-c1-s2",
  "title": "九点的证词",
  "entry": ["wu-claims-east-exit", "blackout-at-2050"],
  "requiredTurns": ["witness-describes-sighting", "defense-introduces-blackout", "witness-admits-reflection"],
  "exit": ["sighting-confirmed", "identity-unconfirmed", "direction-unconfirmed"],
  "forbiddenEstablishedClaims": ["defendant-left-east-exit", "defendant-is-innocent"],
  "castIds": ["judge", "wu", "lin", "shen"],
  "backgroundId": "courtroom"
}
```

以上 ID 是计划里的语义引用，不是新的编辑器 Token，也不在目录显示。第一版可以把计划留在生成草稿中；项目格式尚未决定前，不要把完整账本硬塞进 `ScriptDocument.summary`。

## Skill 执行流程

1. **提取**：从原文抽取账本。把人物的证词记作 `claim`，把叙述者明确给出的事件记作 `established`；冲突并列保留，不擅自裁决。标出原文未覆盖的空白。
2. **规划**：生成作品、章节、场景大纲，并为每场生成契约。检查顺序、引用、时间线、人物在该时点能知道什么，以及结尾是否为下一场提供入口。
3. **逐场写作**：模型只拿本场契约、相关原文片段、账本相关项、相邻场景出口/入口和 Adapter 能力表。长篇不再每次重复发送完整 60,000 字故事。确需补充上下文时按引用提取。
4. **检查与修复**：程序执行结构和能力硬校验；模型再做独立语义核对并给出定位到场景/台词的疑点。只重写失败场景，修改大纲时按依赖标记受影响的场景，而非总是清空全部。
5. **导入**：通过现有 `createProjectFile`、Adapter Validator 和 Compiler。保留当前作品备份；作者改过的台词不因重新检查而被悄悄覆盖。

## 校验分工

**程序硬门槛**：JSON 形状、稳定 ID、章节与场景顺序、引用存在且唯一、人物与资源白名单、每个动作的角色能力、ScriptDocument 校验、编译成功、项目文件往返一致。已有代码承担其中大部分。

**语义疑点（警告，不装作形式证明）**：时间前后矛盾、人物提前知道线索、证词被叙述成既定事实、推断越过证据强度、场景没有完成契约的出口、重复揭示同一转折。诊断要展示触发的账本项与具体台词，允许作者接受、改写或标记为有意悬念。模型自检不能被当作事实证明。

**改编模式差异**：忠实改编禁止把 `invented` 伪装成原作事实；允许扩写可以增加过渡和对白，但新增关键事件须显式列出；原创续写允许增加关键事件，但仍要保持已确定事实与人物知识连续。

## 最小实现顺序

1. 在 `packages/story-ai` 定义并校验 `StoryLedger` 和 `SceneContract`，给大纲与场景建立稳定 ID。先用两部内置案例作 fixture。
2. 把现有大纲请求拆成“事实账本/大纲 → 场景契约”，在界面显示可编辑的场景目标与结尾状态；目录本身不增加层级。
3. 逐场生成改为按契约打包上下文，保留现有取消、失败续跑、备份和密钥处理。
4. 接入语义诊断与单场重生成。首先验证：改掉《九点的影子》的停电时间能定位受影响场景；把《消失的十三秒》的缺失内容写成确知事实会给出警告。

第一版成功标准：两部案例均可从梗概稳定生成完整项目，硬校验与编译通过；人物不会提前知道证据；结论不会强于已给证据；作者可以只修一场并保留其他场景。不要用“写得像不像真人”替代这些可检查的验收条件。

## 与普通 Skill 的边界

Skill 负责创作判断、步骤安排、提示词和语义复核；可复用脚本负责 JSON 契约、ID、引用、白名单、差异和项目导出。网页与 Skill 调用同一套验证函数，避免形成两种剧本格式。模型和平台可替换，不把某个提供商写死为生成逻辑的一部分。
